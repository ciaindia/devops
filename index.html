1. DevOps Basics

What is it? DevOps is a set of practices combining software development (Dev) and IT operations (Ops).

Why is it used? To shorten the development lifecycle and provide continuous delivery with high quality.

Key Terms
  • CI (Continuous Integration): Automatically building and testing code on every commit.
  • CD (Continuous Delivery): Code is always in a deployable state.
  • Continuous Deployment: Every change passing tests is automatically deployed to production.
  • Infrastructure as Code (IaC): Managing infrastructure through machine-readable definition files.
  • Monitoring & Logging: Tracking system health and recording events.
  • Containers & Cloud: Packaging apps (Docker) and running them on rented servers (AWS, GCP).
Plan → Code → Build → Test → Release → Deploy → Operate → Monitor
Interview Tip DevOps is not a tool; it's a culture and methodology focusing on automation and collaboration between Dev and Ops teams.

4. IP Address Classes

Important Note Class A, B, and C are historical classful IPv4 categories. Modern networks primarily use CIDR (Classless Inter-Domain Routing). Beginners encounter these terms often, but they are obsolete.
ClassRangeDefault MaskCIDR
Class A1.0.0.0 – 126.255.255.255255.0.0.0/8
Class B128.0.0.0 – 191.255.255.255255.255.0.0/16
Class C192.0.0.0 – 223.255.255.255255.255.255.0/24

CIDR Examples:
10.0.0.0/8 (16 million+ IPs)

192.168.0.0/16 (65,536 IPs)
192.168.1.0/24 (256 IPs, common in home networks)

5. Private IP Addresses

What is it? IP ranges reserved for internal networks (LAN/VPC) that cannot be routed on the public internet.

Private IPv4 Ranges
  • 10.0.0.0/8 (10.0.0.0 - 10.255.255.255)
  • 172.16.0.0/12 (172.16.0.0 - 172.31.255.255)
  • 192.168.0.0/16 (192.168.0.0 - 192.168.255.255)

Example: Your home router might be 192.168.1.1 and your laptop 192.168.1.100.

Interview Tip A Private IP is used inside a local network. A Public IP is assigned by an ISP and is visible on the internet. NAT (Network Address Translation) allows private IP devices to access the internet using a single public IP.

6. Localhost

What is it? A hostname that means "this computer". It resolves to the local loopback address.

localhost → 127.0.0.1 → current machine
Example Accessing http://localhost:8080 is exactly the same as accessing http://127.0.0.1:8080 on your own machine.
127.0.0.1 vs 0.0.0.0
  • 127.0.0.1: Local loopback address. Only accessible from inside the machine itself.
  • 0.0.0.0: Represents "all IPv4 interfaces" when a server binds to it. Accessible from the outside network.

7. Ports

What is it? A logical endpoint. While an IP identifies the machine, a port identifies the specific service running on it.

Why is it used? To allow one machine to run multiple services (web server, database, SSH) simultaneously.

IP + Port = Socket Example: 192.168.1.10:8080 (IP is 192.168.1.10, Port is 8080)
Interview Tip A port is not an application itself. A process/service listens on a port. If a port is "in use", another process is already listening there.

8. Hosts File

What is it? A local file that maps hostnames to IP addresses manually, bypassing DNS.

Locations:

  • Linux/Mac: /etc/hosts
  • Windows: C:\Windows\System32\drivers\etc\hosts
Example 
127.0.0.1    myapp.local
192.168.1.20 server.local
myapp.local → hosts file lookup → 127.0.0.1 → local machine

Test it with: curl http://myapp.local

Interview Tip The OS checks the hosts file before querying the DNS server. It is highly useful for local testing before deploying DNS records.

9. DNS (Domain Name System)

What is it? The phonebook of the internet. It translates human-readable domain names into IP addresses.

example.com → DNS Resolver → DNS Server → 93.184.216.34 (IP address)

Common Record Types:

  • A record: Maps a name to an IPv4 address.
  • AAAA record: Maps a name to an IPv6 address.
  • CNAME: Maps a name to another domain name (alias).
  • MX: Mail exchange record for routing emails.
  • TXT: Text records, often used for domain verification and security.
Commands 
nslookup example.com
dig example.com
host example.com

11. Git

What is it? A distributed version control system.

Why is it used? To track code changes, collaborate, and maintain history.

Code → git add → git commit → git push → GitHub
Important: Docker Port Publishing -p HOST_PORT:CONTAINER_PORT publishes a container port on the Docker host. For example, -p 8080:80 makes a service listening on container port 80 reachable at http://localhost:8080 from the host. Port publishing is configured when the container is created. You cannot add a published port to an already-created container; recreate it with the required -p option, preserving any important data and configuration first.
Important Commands git init (initialize repo)
git clone (copy remote repo)
git status (check state)
git branch / checkout / switch (manage branches)
git pull / push (sync with remote)
Interview Tip Git is the tool running locally. GitHub/GitLab are web-based hosting services for Git repositories.

12. Docker

What is it? A platform to develop, ship, and run applications inside isolated environments called containers.

Why is it used? "It works on my machine" → Docker ensures it works everywhere identically.

Browser → localhost:8080 → Docker Host Port 8080 → Container Port 80 → Nginx
Important Commands

docker run -d -p 8080:80 nginx

13. Dockerfile

What is it? A text file with instructions on how to build a Docker image.

Example Dockerfile 
FROM nginx:alpine
WORKDIR /usr/share/nginx/html
COPY . /usr/share/nginx/html
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
  • FROM: Base image.
  • WORKDIR: Sets the working directory inside container.
  • COPY: Copies files from host to container.
  • RUN: Executes commands during the build process.
  • EXPOSE: Documents the port the container listens on.
  • CMD: Default command executed when container starts.

14. Docker Compose

What is it? A tool for defining and running multi-container Docker applications using a YAML file.

Why is it used? Instead of running 5 long `docker run` commands, you define everything in `docker-compose.yml`.

Nginx + Prometheus + Grafana + Loki + Alloy → defined in docker-compose.yml
Commands 
docker compose up -d
docker compose ps
docker compose logs -f
docker compose down

Interview Point: Docker Compose automatically creates a default network, allowing services to communicate with each other using their service names as hostnames.

15. Nginx

What is it? A high-performance web server, reverse proxy, and load balancer.

Browser → Nginx (Reverse Proxy) → Internal Application (e.g. Node.js on port 3000)
Static Website Web Root On many Ubuntu/Debian Nginx packages, the default website files are served from /var/www/html/. The default page is commonly index.nginx-debian.html. Confirm the active configuration before assuming the document root: 
nginx -T | grep -n "root "
ls -la /var/www/html/
A file copied into the web root is deployed, but Nginx must also be running and listening on the expected port before a browser can load it.
Basic Configuration 
server {
    listen 80;
    server_name example.com;
    
    location / {
        proxy_pass http://localhost:3000;
    }
}

16. GitHub Actions

What is it? GitHub's native CI/CD platform.

Why is it used? To automate software workflows (build, test, deploy) triggered by GitHub events.

git push → GitHub Actions triggers Workflow → Checkout → Build → Test → Deploy
Key Terms
  • Workflow: Defined in .github/workflows/cicd.yml.
  • Job: A set of steps executing on the same runner.
  • Step: Individual task (script or action).
  • Runner: The server that runs your workflow.
Minimal Workflow Example 
name: CI

on:
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: echo "Repository checked out"
The workflow file is stored in .github/workflows/. The on section defines the trigger, jobs defines work to run, runs-on selects a runner, and steps are executed in order.

17. Self-hosted GitHub Runner

What is it? Your own machine/server configured to run GitHub Actions jobs instead of using GitHub's cloud instances.

Why is it used? For accessing private network resources, custom hardware, or saving costs.

GitHub → Workflow Event → Self-hosted Runner (Your Server) → Local Docker Executes Job
Interview Tip A self-hosted runner executes jobs in the environment where the runner is installed. It can run Docker commands only when Docker CLI is installed and the runner has permission to access a Docker daemon/socket. A runner inside a basic Ubuntu container does not automatically control Docker Desktop on the host.

18. Prometheus

What is it? An open-source systems monitoring and alerting toolkit built on a Time-Series Database (TSDB).

Why is it used? To scrape, store, and query metrics (CPU, Memory, HTTP requests).

Application Exporter → Prometheus (Scrapes targets periodically) → Grafana
Exporters Small binaries that expose application metrics in a format Prometheus understands (e.g., Node Exporter for Linux stats).

19. Grafana

What is it? An open-source analytics and interactive visualization web application.

Why is it used? It connects to data sources like Prometheus and Loki to build beautiful dashboards and alerts.

Prometheus (Metrics) → Grafana Loki (Logs) → Grafana

Interview Point: Grafana itself does not collect data. It queries and visualizes data stored in external backends (Data Sources).

20. Loki

What is it? A horizontally scalable, highly available log aggregation system inspired by Prometheus.

Why is it used? Traditional log systems index full text. Loki only indexes labels for logs, making it extremely lightweight and cost-effective.

Container Logs → Alloy → Loki → Grafana

21. Grafana Alloy

What is it? Grafana's vendor-neutral observability collector (OpenTelemetry native).

Why is it used? It replaces multiple agents (like Promtail). It collects metrics, logs, and traces, and forwards them to backend systems (Prometheus, Loki, Tempo).

Docker Logs/Metrics → Alloy → Loki / Prometheus
Interview Tip Alloy is primarily a collector agent. It is not just a logging equivalent of Node Exporter; it acts as a universal pipeline for all telemetry data.

22. Monitoring and Alerting

What is it? Observing system state and reacting to anomalies.

  • Metrics: Numeric measurements over time (CPU at 90%).
  • Logs: Discrete event records (User login failed).
  • Alerts: Notifications sent when thresholds are breached.
Application → Metrics → Prometheus → Grafana → Logs → Alloy → Loki → Grafana → Alerts → Grafana Alerting System (Email, Slack)

Why is it used? To provision and manage cloud infrastructure using declarative configuration files (.tf).

Terraform → Cloud Provider API (GCP/AWS) → Provisioned Infrastructure
Core Commands terraform init: Initialize working directory.
terraform fmt: Format code.
terraform validate: Check syntax.
terraform plan: Show execution plan.
terraform apply: Apply changes.
terraform destroy: Delete infrastructure.

Interview Point: Terraform uses a terraform.tfstate file to map real-world resources to your configuration. State management is crucial.

30. Troubleshooting Scenarios

Practical steps when things go wrong.

Scenario: Website not opening (Port 8080)
  1. Is container running? docker ps
  2. Is port listening? ss -tulpn | grep 8080
  3. Check container logs: docker logs <container>
  4. Test locally from server: curl http://localhost:8080
  5. Check Nginx status: systemctl status nginx
  6. Check cloud firewall / security groups allowing port 80/8080.
  • Docker container not starting: Run docker logs or start it interactively without detached mode (remove -d) to see stdout immediately.
  • Port already in use: Find PID with ss -tulpn and use kill <PID> if safe.
  • DNS not resolving: Check nslookup <domain> or edit /etc/hosts.
  • Cannot SSH: Ensure port 22 is open, SSH service is running, and your private key permissions are secure (chmod 400 key.pem).
  • GitHub Actions failure: Click the failed step in GitHub UI and read the output logs.
  • Self-hosted runner job stays queued: Check that the runner is online and every label in runs-on matches a label assigned to that runner.
  • Deployment says file not found: Check the repository layout and use the correct path after actions/checkout.
  • Deployment succeeds but curl to localhost fails: The file copy may have succeeded while Nginx is stopped or not listening. Check nginx -t, ps aux | grep nginx, and ss -lntp | grep :80.
  • Website works inside container but not from host: Check whether the container was created with a port mapping such as -p 8080:80. A container's localhost is not the host computer's localhost.
  • Self-hosted runner offline: SSH into VM, check the run.sh script or journalctl if it runs as a service.
  • Prometheus target down: Check http://target_ip:9100/metrics via curl. Check firewall rules.
  • Grafana cannot connect to Prometheus: Ensure Prometheus URL is correct in Data Source settings (e.g., http://prometheus:9090 in Docker network).
  • Loki logs not appearing: Ensure Alloy is running, checking its own logs, and that timestamps are correct on host machines.

31. Practical: GitHub Self-hosted Runner + Nginx in One Ubuntu Container

Objective: Run Nginx and a GitHub self-hosted runner inside the same Ubuntu Docker container. When code is pushed to the GitHub repository's main branch, GitHub Actions sends a job to that runner. The runner copies index.html into Nginx's web root.

Developer → git push → GitHub Repository → GitHub Actions Workflow → Self-hosted Runner (inside Ubuntu container) → Copy index.html to /var/www/html/ → Nginx serves the updated page
Important: One Container Setup In this practical, Ubuntu, the GitHub runner, and Nginx are inside the same Ubuntu container. Docker CLI is not required inside that container for a simple file-copy deployment. Docker Desktop manages the Ubuntu container from the host computer.

31.1 Install runner dependencies

Run these commands as root inside the Ubuntu container:

apt update
apt install -y curl git tar gzip libicu-dev
PackagePurpose
curlDownload the GitHub Actions runner archive.
gitCheck out the repository source code during a workflow.
tarExtract the runner archive.
gzipHandle the gzip-compressed runner archive.
libicu-devProvides ICU libraries needed by the .NET runtime used by the runner on this setup.
Dependency Note These are the basic packages used in this practical, not a universal dependency list for every Linux distribution or runner release. If the runner reports missing libraries, run its dependency installer as root: /home/runner/actions-runner/bin/installdependencies.sh. Package names and runtime dependencies can differ between Ubuntu releases.

31.2 Create a dedicated runner user

useradd -m -s /bin/bash runner
mkdir -p /home/runner/actions-runner
chown -R runner:runner /home/runner

Use a non-root account to run workflow jobs. The runner user needs write permission to the Nginx document root for this simple deployment:

chown -R runner:runner /var/www/html

Note: Changing ownership is a simple lab setup. For production, prefer a narrowly scoped group or deployment permission rather than making broad ownership changes to web directories.

31.3 Download the GitHub runner

  1. Open the GitHub repository.
  2. Go to Settings → Actions → Runners.
  3. Select New self-hosted runner, then choose Linux and the correct architecture (usually x64 for x86_64).
  4. Use the download URL, version, and checksum displayed by GitHub. Runner versions change, so do not assume an old example URL is current.

As the runner user, create the directory and extract the archive:

su - runner
mkdir -p ~/actions-runner
cd ~/actions-runner

# Run the exact curl download command shown by GitHub.
# Then extract the downloaded archive, for example:
tar xzf actions-runner-linux-x64-*.tar.gz

31.4 Configure and start the runner

On the GitHub runner setup page, copy the repository URL and use the temporary registration token shown in the configuration command:

./config.sh \
  --url https://github.com/OWNER/REPOSITORY \
  --token YOUR_TEMPORARY_REGISTRATION_TOKEN

Follow the prompts. The default runner group and default work folder are suitable for this lab. You can optionally add a custom label, but if you do, that label must also appear in the workflow's runs-on list.

Registration Token Security The registration token is temporary and is used to register the runner; it is not a permanent Personal Access Token. Do not publish it, paste it into workflow files, or commit runner credential files such as .credentials and .runner to Git. If a token is exposed, generate a fresh one before registration.

Start the runner as the runner user:

./run.sh

Successful startup displays messages similar to:

Connected to GitHub
Listening for Jobs

Keep this process running while testing. Closing the terminal or stopping the container stops this foreground runner process. For a long-running environment, configure the runner as a service using GitHub's documented service instructions.

31.5 Create the repository files

For this example, index.html is in the repository root:

cicddemo/
├── index.html

    └── workflows/
        └── deploy.yml

Example index.html:

<!DOCTYPE html>
<html lang="en">

  <meta charset="UTF-8">
  <title>GitHub Runner Demo</title>
</head>

  <h1>Hello from GitHub Actions!</h1>
  <p>Deployed to Nginx on Ubuntu.</p>

31.6 Create the workflow

Create .github/workflows/deploy.yml:

name: Deploy HTML to Nginx

on:
  push:
    branches:
      - main

permissions:
  contents: read

jobs:
  deploy:
    runs-on: [self-hosted, linux, x64]

    steps:
      - name: Checkout source code
        uses: actions/checkout@v4

      - name: Display runner information
        run: |
          echo "Running on Ubuntu Docker Container"
          hostname
          whoami
          pwd
          ls -la

      - name: Deploy HTML
        run: |
          cp index.html /var/www/html/index.html

      - name: Verify deployment
        run: |
          ls -l /var/www/html/
          cat /var/www/html/index.html
          echo "HTML file deployment successful"
Why these runner labels? The runner automatically receives labels such as self-hosted, linux, and x64. The workflow uses those labels in runs-on. If you add a custom label during runner configuration, include the same label in runs-on; otherwise, GitHub may leave the job waiting for a matching runner.

31.7 Understand the deployment steps

  • Push trigger: A push to main starts the workflow.
  • Checkout: actions/checkout downloads the repository into the runner's job workspace.
  • Deploy: cp index.html /var/www/html/index.html copies the checked-out file to Nginx's document root.
  • Verify: ls and cat confirm that the deployed file exists and contains the expected content.

31.8 Push and test

git add .
git commit -m "Add HTML deployment workflow"
git push origin main

Open the repository's Actions tab and inspect the workflow run. A successful Deploy HTML step confirms that the file-copy command completed.

31.9 File deployment versus website availability

Important Troubleshooting Lesson A file can be copied successfully even when Nginx is stopped. File deployment and HTTP availability are separate checks. A successful cp proves the file was copied; it does not prove that Nginx is running or reachable.

Inside the same Ubuntu container, check Nginx:

nginx -t
ps aux | grep nginx
ss -lntp | grep ':80'
curl -I http://localhost

If Nginx is not running, start it in the container using the appropriate method for that container. In a basic Ubuntu container without systemd, a common foreground command is:

nginx -g 'daemon off;'

Use a process manager or container entrypoint that keeps the required processes alive if both the runner and Nginx must run continuously in one container.

31.10 Access Nginx from the host computer

localhost inside the Ubuntu container refers to that container, not the host computer. To open Nginx from the host browser, the Ubuntu container must have been created with a published port, for example -p 8080:80. Then open http://localhost:8080 on the host.

docker run -it -p 8080:80 ubuntu

Important: Port publishing is set when a container is created. It cannot be added to an existing container in place. Recreate the container with the required port mapping and preserve the runner configuration and website data before removing the old container.
